# 杜衡阁公众号后续编码实施计划

> 文档状态：待确认后执行
>
> 依据：《杜衡阁公众号运营回复与双小程序增长最终方案》v1.0
>
> 编制日期：2026-09-08
>
> 原则：先保证知行日知、知行策论正式入口稳定，再接公众号；每个开发单元独立执行“实现 → 验证 → 归档 → 提交并推送”。

## 1. 当前基线

### 1.1 已完成，可以直接复用

- 知行日知与知行策论保持两个独立前端，共用一个 FastAPI 后端和一个管理后台。
- 知行日知已经具备已审核文章、5 题分辑、同文合集、长期重点和公开学习入口。
- 知行策论已经具备已发布原文、公共三刀示范、短练习和公开学习入口。
- 内容运营后台已经具备公众号、小红书、知乎、微信视频号四类渠道草稿。
- 发布包已经绑定结构化学习入口，而不是不可校验的自由文本 URL。
- 发布前已经检查母内容、产品、H5 路径、小程序路径、场景值、承接词、渠道正文和归因参数。
- 当前归因字段已经包含 `channel/campaign/content/product/entry`。

### 1.2 尚未完成

- 两个 H5 的正式域名、HTTPS、线上 API 和服务器部署尚未完成验收。
- 两个微信小程序尚未完成开发者工具导入、真机联调、体验版和提审。
- 现有小程序页面尚未完整消费渠道参数与小程序码 `scene`，入口打开事件也未形成完整漏斗。
- 没有公众号账号、回复模板、意图规则、入口绑定、回复发布版本等正式数据模型。
- 没有确定性关键词路由、冲突检测、失效降级和回复预览。
- 没有微信公众号服务器回调接入，也没有微信消息验签、解密、去重和重试保护。
- 内容发布包目前只记录整体发布状态，尚未按渠道回填真实链接、时间与失败原因。
- 尚未生成正式小程序码或渠道二维码；当前只有经过校验的场景值。
- 尚未形成从公众号触达到小程序完成学习的 D1/D7 漏斗。

## 2. 总体开发顺序

```text
R0 正式运行基础
  ↓
R1 统一入口与归因协议
  ↓
R2 公众号配置数据底座
  ↓
R3 确定性回复路由
  ↓
R4 公众号后台人工配置包
  ↓
R5 微信服务器回调接入（以权限为前提）
  ↓
R6 渠道发布记录与二维码
  ↓
R7 端到端验收和首批运营上线
  ↓
P2 留存增强 / P3 智能化
```

不建议跳过 R0 直接接公众号。否则回复中的链接和小程序路径没有稳定线上目标，后续每次改动都会产生失效入口。

## 3. 第一阶段：正式运行基础

### R0：H5 部署、小程序真机联调与提审收口

**目标**

让知行日知和知行策论先拥有稳定、可重复验证的 H5 与微信小程序入口。

**开发任务**

1. 整理安全的一键部署命令，覆盖共用后端、管理后台、两个 H5 和静态资源。
2. 修正更新脚本中的危险回退逻辑；服务器代码无法快进更新时直接停止，不自动覆盖服务器修改。
3. 增加发布前检查工具，检查生产环境变量、AppID、API 地址、构建产物、域名、HTTPS 和关键路由。
4. 为两个应用分别生成 H5 与微信小程序发布产物，避免同一应用的 H5/小程序构建相互覆盖 `dist`。
5. 验证 `/theory/`、`/shenlun/`、`/manage/`、`/api/*` 和健康检查。
6. 用微信开发者工具导入两个产物，完成启动、页面跳转、API 请求、游客学习、登录同步和异常页面真机验证。
7. 收口两个小程序的服务类目、隐私指引、用户协议、截图、测试账号和提审说明。

**必要性**

公众号所有回复最终都必须落到真实产品。正式入口不稳定时，公众号能力越丰富，传播无效链接和错误内容的风险越大。

**完成标准**

- 两个 H5 通过 HTTPS 可访问，刷新深层路由不出现 404。
- 两个小程序使用正式 API 域名，真机不依赖关闭域名校验。
- 公开学习入口无需登录即可完成；登录后游客记录能够同步。
- 构建、部署、回滚和验收命令均有文档和检查结果。
- 体验版材料完整，外部阻塞项被单独列出。

**预计工作量**：1～2 个开发日；备案、微信域名配置和平台审核时间不计入。

## 4. 第二阶段：公众号 P0——把内容准确送到产品

### R1：统一入口解析与渠道事件

**目标**

公众号、内容文章、二维码和外部平台使用同一套入口参数，并且任何入口失效时都有安全降级。

**开发任务**

1. 新增统一入口解析服务，接收：

   ```text
   product / entry / section / channel / campaign / content
   ```

2. 服务端依次校验产品一致、入口存在、母内容已发布、入口已开放、时间有效和分辑有效。
3. 返回明确目标页或安全降级页；不允许将知行日知内容送入知行策论，反之亦然。
4. 两个小程序页面接收普通 query 与小程序码 `scene`，解析后进入对应文章、分辑或三刀示范。
5. 两个 H5 接收同一协议，并保留渠道参数直到首次有效学习事件。
6. 增加 `entry_link_opened`、`miniapp_learning_started`、`miniapp_learning_completed` 事件；所有事件携带五类归因字段。
7. 对未知参数、过期入口、撤审内容和接口异常编写自动化测试。

**必要性**

U05 已经能生成结构化入口，但终端还必须真正理解和验证这些参数，否则“看起来正确的发布包”仍可能把用户送错位置。

**完成标准**

- 同一发布包的 H5 与小程序入口进入同一个学习内容。
- 无效、串线、过期和撤审入口均进入可理解的安全页面。
- 打开、开始和完成事件可按内容与渠道追溯。

**预计工作量**：1.5～2 个开发日。

### R2：公众号配置数据底座与管理后台

**目标**

把最终方案里的欢迎语、菜单、核心意图和入口绑定变成可审核、可回退的数据，而不是写死在代码中。

**建议模型**

```text
wechat_accounts
wechat_reply_templates
wechat_intent_rules
wechat_entry_bindings
wechat_reply_releases
```

首发不创建复杂画像、连续打卡和对话状态表。只有微信实际接入并证明需要后，再增加 `wechat_users` 和最小会话状态。

**开发任务**

1. 公众号账号配置只保存非敏感标识和能力开关；AppSecret、Token、EncodingAESKey 只从生产环境变量读取。
2. 回复模板支持欢迎、菜单、今日、时政、申论、兜底、异常七类；保存版本和启停状态。
3. 意图规则支持关键词、别名、匹配类型、优先级、启停和冲突检测。
4. 入口绑定只能选择当前有效的知行日知或知行策论学习入口。
5. “今日”使用运营人员已审核并明确选中的内容，不按抓取时间自动发布。
6. 发布版本保留快照、操作者、发布时间和回退版本。
7. 管理后台提供列表、编辑、预览、冲突提示、发布和版本回退。
8. RBAC 拆分查看、编辑和发布权限；发布动作记录审计日志。

**必要性**

运营内容每天变化，写死关键词和链接会使每次换内容都依赖发版。版本与回退能力也是处理错误回复和内容撤审的最低安全保障。

**完成标准**

- 运营人员不改代码即可替换“今日”内容。
- 未发布模板和无效入口不能对外生效。
- 规则冲突在发布前被阻断。
- 任一正式版本可回退到上一稳定版本。

**预计工作量**：2～3 个开发日。

### R3：确定性回复路由与预览器

**目标**

用简单、可解释、可测试的规则稳定识别用户需求；首发不引入 AI 自由问答。

**首发意图**

| 意图 | 展示关键词 | 兼容别名 | 结果 |
| --- | --- | --- | --- |
| 今日 | 今日 | 今天、今日学习、今日一练 | 当期唯一主任务 |
| 时政 | 时政 | 日知、时政学习 | 知行日知入口 |
| 申论 | 申论 | 策论、申论学习、三刀 | 知行策论入口 |
| 菜单 | 菜单 | 帮助、导航、开始 | 四类入口说明 |

数字关键词只作为旧内容兼容规则，不在新欢迎语中要求用户记忆。

**开发任务**

1. 文本标准化：全半角、空白、常见标点和大小写处理。
2. 匹配顺序：精确词 → 明确别名 → 已配置前缀/包含规则 → 兜底。
3. 同优先级多命中时阻止规则发布，不在运行期随机选择。
4. 路由结果再次调用 R1 入口解析，防止回复缓存绕过内容状态。
5. 提供管理后台“输入一条消息看最终回复”的预览器。
6. 记录 `wechat_intent_matched` 与 `wechat_fallback`，但默认不长期保存完整用户原始文本。
7. 增加敏感输入、超长输入、图片/语音等非文本消息和服务异常测试。

**必要性**

首发的目标是准确分流，而不是显得智能。确定性路由更容易审核、回归测试和快速回退。

**完成标准**

- 核心意图命中唯一且可解释。
- 未识别输入只返回短兜底，不刷屏、不猜测。
- 回复中的目标入口在发送前完成实时校验。

**预计工作量**：1.5～2 个开发日。

### R4：公众号后台人工配置发布包

**目标**

在尚未接入或暂不适合启用开发者服务器时，也能由运营人员安全地在公众号后台完成欢迎语、关键词和菜单配置。

**开发任务**

1. 从已发布回复版本导出公众号后台配置清单。
2. 输出欢迎语、关键词、命中回复、链接/小程序路径、配置顺序和人工核对项。
3. 输出“公众号实际能力不支持某项功能”时的静态替代文案。
4. 保存人工配置结果、操作者、实际生效时间和后台截图/备注引用。
5. 发布前检查回复字数、唯一 CTA、产品名称、入口状态和未开放功能宣传。

**必要性**

公众号账号类型和接口权限存在差异。人工配置包能让 P0 不被开发者回调能力完全卡住，也为正式回调接入提供可回退的静态方案。

**完成标准**

- 运营人员按照清单可完成一次无歧义配置。
- 每条回复可追溯到模板版本和真实学习入口。
- 开发者回调关闭时仍保留可用的基础分流。

**预计工作量**：1 个开发日。

## 5. 第三阶段：公众号 P1——稳定回复、归因和运营

### R5：微信公众号服务器回调接入

> 只有在账号后台确认具有所需接口能力、并具备微信服务器能够访问的公网回调 URL 后才执行。技术联调可在公众号后台允许时使用公网 IP 加路径；正式上线仍统一切换到已备案的 HTTPS 域名。

**开发任务**

1. 新增独立公众号公共路由，完成服务器 URL 验证。
2. 校验微信签名；启用安全模式时完成消息加解密。
3. 处理关注、取消关注、文本消息和菜单/扫码事件；其他消息类型走统一短回复。
4. 使用微信消息标识与事件字段做幂等去重，正确处理平台重试。
5. 在平台要求的响应时间内完成被动回复；内部异常走安全兜底，不暴露堆栈和密钥。
6. Token、AppSecret、EncodingAESKey 全部进入服务器密钥配置，不进入数据库导出、日志或 Git。
7. 对原始消息日志脱敏，设置保留期限；仅保存运营分析所需字段。
8. 增加限流、重放保护、告警和回调健康检查。
9. 用微信测试号或正式号灰度验证，再切换正式回复。

**必要性**

只有开发者回调稳定后，确定性路由、版本回退、实时入口校验和统一事件记录才会真正作用于公众号消息。

**完成标准**

- 签名错误、重放和重复消息不会触发错误业务行为。
- 关注、四类核心词、兜底和异常均通过微信真实环境验收。
- 关闭回调后可按 R4 静态配置回退。

**预计工作量**：2～3 个开发日，不含微信平台审核和权限等待。

### R6：Campaign、二维码与逐渠道发布记录

**目标**

把“生成内容”升级为“知道实际发到了哪里、带来了什么有效学习”。

**建议演进模型**

```text
content_campaigns
channel_entry_links
channel_qr_scenes
publication_records
```

继续演进现有 `content_publish_packages`，不另建重复发布包系统。

**开发任务**

1. 独立维护 campaign 名称、目标产品、时间范围、状态和备注。
2. 从结构化入口生成渠道链接和小程序码任务；实际调用能力不可用时导出人工生成清单。
3. 将小程序码文件与场景值、入口版本绑定，入口撤审时标记不可继续投放。
4. 按公众号、小红书、知乎、微信视频号分别回填实际发布 URL、时间、状态和失败原因。
5. 记录 `content_published`、`content_publish_failed` 和 `entry_link_opened`。
6. 后台显示曝光数据可用性，不把“无法获取曝光”错误显示为零曝光。
7. 提供单渠道紧急下线和整包入口降级。

**必要性**

只有逐渠道记录实际发布结果，才能区分“草稿已准备”“已经发布”“用户成功进入产品”三个完全不同的状态。

**完成标准**

- 任一访问可追溯到渠道、campaign、母内容、产品和入口。
- 发布失败与未发布不会计为已触达。
- 入口撤回后旧链接和旧码进入安全降级页。

**预计工作量**：1.5～2.5 个开发日。

### R7：首批内容端到端验收与灰度上线

**目标**

用真实内容而不是样例数据验证完整运营链路。

**验收样本**

- 知行日知：1 个当期学习内容、1 个长期重点专题。
- 知行策论：1 篇公开三刀示范和对应短练习。
- 每个样本至少生成公众号、小红书、知乎、微信视频号四种变体。

**验收路径**

```text
母内容审核
→ 学习入口发布
→ 内容发布包生成
→ 公众号回复/文章承接
→ H5 或小程序打开
→ 开始学习
→ 完成学习
→ 后台查看归因
→ 撤审后验证安全降级
```

**完成标准**

- 新用户一屏内理解价值并开始一个任务。
- “今日、时政、申论、菜单”均命中预期结果。
- 双产品、双端、四渠道不串线。
- 完成事件和 D1 回访基线可以计算。
- 有异常回退、运营 SOP 和值班联系人。

**预计工作量**：1～2 个开发日。

## 6. P2 与 P3 暂不进入首发排期

### P2：有留存数据后再做

- “我的／继续学习”：必须先确认公众号身份与小程序账号能否可靠关联；不能关联时只跳转产品首页或最近本机记录。
- D1/D7 看板：必须先保证入口事件、开始事件和完成事件稳定采集。
- 已发布内容搜索：只搜索仍可访问的审核内容。
- 学习周报与战绩卡：只展示真实个人数据，不展示未经验证的全国排名或人数。
- 社群入口：确认有人持续运营、群规则和隐私边界后再开放。

### P3：规模化后再做

- 语义搜索和智能兜底。
- 内容变体辅助生成及跨平台一致性校验。
- A/B 测试、自动复盘和渠道预算建议。
- 新题型产品接入统一入口协议。
- 半自动外部发布；AI 永远不能绕过人工审核直接发布。

## 7. 建议排期与里程碑

按单人串行开发估算，不含备案、微信平台审核、真实内容教研和运营人工发布时间：

| 里程碑 | 开发单元 | 预计工作量 | 结果 |
| --- | --- | ---: | --- |
| M0 正式入口可用 | R0 | 1～2 日 | 双 H5、双小程序可联调/提审 |
| M1 内容可准确承接 | R1 | 1.5～2 日 | 所有渠道使用统一入口协议 |
| M2 公众号配置可维护 | R2～R4 | 4.5～6 日 | 模板、规则、绑定、预览、人工配置包 |
| M3 公众号正式接入 | R5 | 2～3 日 | 微信真实消息稳定路由 |
| M4 运营闭环可度量 | R6～R7 | 2.5～4.5 日 | 逐渠道发布记录与端到端验收 |

P0＋P1 总开发量约 12～17.5 个开发日。现有 U05 能力已经纳入基线，不重复建设。

## 8. 每个开发单元的固定交付要求

每个单元必须同时交付：

1. 功能实现与必要的数据兼容处理；
2. 后端自动化测试、前端类型/代码检查及相关生产构建；
3. 真实失败场景测试，不只测试成功路径；
4. 数据与接口文档；
5. 本单元完成记录、验证证据、明确限制和下一单元；
6. 独立 Git 提交并推送，不夹带工作区其他修改；
7. 涉及公众号后台、服务器或微信开发者工具的人工步骤形成可复现清单。

## 9. 需要确认的事项

### 9.1 启动 R0 前必须确认

1. **生产域名与服务器登录方式**：最终 H5/API 使用哪个域名；服务器 IP、SSH 用户和认证方式如何提供。公网 IP 可以先用于公众号回调技术验证，但不能替代两个小程序的正式 HTTPS API 域名。不要把密码或私钥写入项目文档。
2. **备案当前状态**：备案未完成时先完成本地发布包和微信体验版联调，不把临时 HTTP 地址当正式入口。
3. **两个小程序的正式对应关系**：当前代码记录为知行日知 `wx987f43ac6993012e`、知行策论 `wx5d75ef07d8241d84`，需要在微信后台再次核对名称、主体和 AppID。
4. **首批验收内容**：分别指定知行日知的“当期内容＋长期重点”和知行策论的首篇三刀示范；若暂不指定，开发阶段使用已审核测试内容，正式运营前再替换。

### 9.2 启动 R2～R5 前必须确认

1. **杜衡阁账号类型与认证状态**：订阅号/服务号、个人/企业主体、是否认证，以及公众号后台实际显示的接口权限。
2. **公众号与两个小程序的关联情况**：分别核对可跳转的小程序 AppID；不能只确认其中一个。
3. **接入策略**：推荐先用公众号后台人工配置完成 P0；开发者回调可在公网 IP 回调验证通过后开始联调，正式运营时再切换到 HTTPS 域名。需要确认是否接受该顺序。
4. **消息安全模式**：以公众号后台可用配置为准；正式接入推荐安全模式，密钥只放服务器环境变量。
5. **异常反馈渠道**：确定真实可用的联系邮箱或人工回复处理人，用于内容纠错和入口故障。

### 9.3 可以采用默认值、暂不阻塞开发

- 首发核心意图使用“今日、时政、申论、菜单”；“我的”到 P2 再开放。
- 新关注回复只有一个主动作：“今日”。
- 公众号内不答完整题，不实现第二套练习前端。
- 首发规则使用确定性关键词，不接 AI 自由问答。
- 运营人员人工发布四个平台，系统只生成、检查和记录。
- 公众号身份与小程序账号首发不强行合并；有可靠 UnionID/授权条件后再实施。
- 数据先看入口触发、打开、学习开始、学习完成和 D1/D7，不做虚构曝光补值。
- 首发不做付费、社群、排行榜、裂变解锁和主动召回。

## 10. 建议现在确认的最小决策

为了立即开始 R0，只需要先确认以下四点：

1. 两个 AppID 对应关系是否正确；
2. 正式域名是什么，备案目前处于什么状态；
3. 是否接受“先人工配置公众号 P0，后开发者回调 P1”的接入顺序；
4. 首批内容由你指定，还是先用系统中已审核内容完成技术验收。

其余事项可以在 R0、R1 开发期间继续核对，不必一次性决定。
